# Imported workflow patterns and execution contracts

Issue #105 requires the workflow patterns from `WRKFLW`, `workflows`, and this executor to be consolidated. The original four catalog entries did not meet that requirement. The canonical engine now includes the original BuildPlan/type contracts and the construction lifecycle adapters below, alongside those entries. This is a pattern and runnable-example migration; it does not recreate the archived web/mobile applications or claim that live services have been deployed.

The archived source is the authority for the patterns. [Source provenance](../../workflows/source_manifest.json) records the observed tree/blob hashes; all 18 inspected source files matched those tree entries. `workflows/source_types.ts` preserves its complete type definitions. `ported/` retains the original API/schema/PRD snapshots for comparison. The original Next.js route imports are historical; the runnable canonical equivalents are `workflows/imported.py`, backed by the modules listed here. There are no missing alias imports in this Python execution path. Upstream graph execution, PDF extraction, general transcription and protocol clients contained simulated/placeholder outputs; those outputs are not treated as working integrations.

## Running the examples

Use the repository's Python dependencies and Node 22 TypeScript compiler setup:

```sh
pip install -r requirements-ci.txt
npm ci --ignore-scripts --prefix tools/typescript-validation
python -m examples.build_plan_workflow --demo --database /tmp/workflow-example.sqlite3
python -m examples.construction_lifecycle --help
```

The demo performs a real local two-task calculation and saves its generated code artifacts. It is explicitly supplied example data, not a claimed AI-generated plan. For source intake, `examples.build_plan_workflow --url ... --database ... --bindings your_app.bindings` imports a trusted application module with `configure(store)`. It supplies `Ingestor`, provider/client settings and task/composite bindings to `ImportedWorkflows`. No function name or Python import is taken from an ingested document. The external YAML definitions are auto-loaded as before.

To use the native engine, register `engine.agents['imported_workflows'] = ImportedWorkflows(...)` and select `build_plan_pipeline`. Its six steps retain intake, summary, plan, compilation, actual execution and saved scaffold generation. For WRKFLW, register `ConstructionWorkflowAgent(lifecycle, authenticated_credentials, confirm=host_confirmation)` as `construction_lifecycle`; select `construction_action` with an explicit operation/parameters or `construction_project_onboarding`. Invitation acceptance, summary review and publication remain separate authenticated operations. The host must authorize actions and supply real recipient identities; a source document cannot replace the authenticated principal or provide its own confirmation. The host confirmation callback must affirm the exact operation/parameters before the AI-facing adapter mutates server state.

## Configuration and limits

- `WorkflowPlanner` reuses the repository's `OPENAI_API_KEY` connector setting; `WORKFLOW_MODEL` selects its model (source default `gpt-4o-mini`). Other providers can implement the planner interface. No paid call was made during automated checks. Provider response schemas and failure paths were tested with controlled HTTP transports.
- Source HTTP requires host-approved origins. Redirects are rejected. Private Google Docs/captions require an authorized OAuth token; direct media transcription requires a real audio/video resource. Vimeo/other webpage extraction needs a host-approved media extractor. Image-only PDFs require explicit OCR; empty text is an error. Resource limits are enforced, but this library is not a hardened multi-tenant document sandbox.
- The upstream BuildPlan lacks composite child membership and loop termination controls. The host supplies `composites` explicitly; missing controls fail. Agent handler names are a local registry, not arbitrary imports. A protocol flag describes a requirement; it grants no tool authority or payment permission. AP2's upstream client did not define a real endpoint/SDK, so the adapter calls a host-configured validating payment client and never invents a wire protocol.
- Construction auth, email/notification delivery, signed object storage, embeddings/vector service, LLM generation and PDF rendering/storage are host-owned adapters. Tests exercise real controlled local bytes, signing, vector indexing/search, delivery receipts and PDF files. They do not prove live S3/email/model delivery, mobile UI parity, or a deployed SaaS. The `generate` adapter must be backed by an actual provider; deterministic fixture summaries are confined to tests.
- The durable notification outbox preserves the exact authorized message for an explicit `retry_notification`; pending listings omit content. Its private database can contain invitation links and project data and must be protected by the host. Only token hashes are used as invitation IDs. SQLite is a local engine store, not a multi-worker hosted transaction service.
- `Repair` callbacks may change a failed operation's technical inputs or restore a host-approved snapshot. They cannot fabricate successful outputs. Construction adapter repair preserves every field of the original authenticated payload, including notification bodies and storage object keys; it may add technical settings without replacing source or destination fields. No-op repairs fail, unchanged invalid operations remain failed, and prior failed attempts remain visible. Completed child outputs are checkpointed within one execution, keyed by composite path and loop iteration; parallel children settle before failed children retry. A changed retry input that would invalidate a completed checkpoint fails for reconciliation. These in-memory checkpoints are not a cross-process resume promise. Observer/persistence and output-binding errors after successful work never trigger replay. Loop termination callbacks must be pure predicates. External service retries must honor idempotency keys. Native steps that create/approve records are not blindly replayed as whole actions; adapter correction and the outbox own recovery.
- A generated Dockerfile is a library packaging artifact. It does not select a deployment target, provide application-specific business handlers, or deploy a service. `deployment_status=scaffold_only` remains explicit even when artifact generation finishes.

Run `pytest` (with `PYTHONPATH` unset) for the actual source/graph/correction/provider/TypeScript/lifecycle checks. Hosted PR validation and any live provider acceptance remain separate from local code validation.
